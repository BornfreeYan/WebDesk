# WebDesk 风险与待确认问题

> 本节记录产品层面尚未确认的风险和待决策事项。技术实现细节（如 z-index 管理、Token 类型选择）由开发阶段解决，不列入此处。

---

## 一、产品定位风险

### Q1: 用户群体是否过窄？
**现状**: 目标用户锁定为"会 fork repo 并配置 GitHub Token 的开发者"。
**风险**: 该群体规模有限，且开发者往往已有自己的书签管理方案（浏览器自带、Notion、Raindrop 等）。WebDesk 的差异化是否足以让他们迁移？
**待确认**: 是否需要明确 WebDesk 相比现有方案的核心优势（除了"桌面交互"外）？

### Q2: "桌面隐喻"对开发者是真需求还是假需求？
**现状**: 核心卖点是"像操作电脑桌面一样管理书签"。
**风险**: 开发者用户可能更看重效率（搜索、标签、快捷键）而非视觉拟物。桌面拖拽对效率的提升是否成立？
**待确认**: 是否需要引入效率功能（如 Command Palette、全局搜索）来平衡视觉体验与实用价值？

---

## 二、功能范围待决

### Q3: 本地轻量应用（便签/番茄钟）是否值得做？
**现状**: Brainstorm 中列为"可选，甚至可以不做"。
**风险**: 便签/番茄钟等功能会显著增加 MVP 复杂度，但对"书签管理器"的核心价值贡献有限。
**待确认**: 
- MVP 是否只做纯书签管理，不做任何本地应用？
- 如果做，第一个本地应用是什么？（便签 vs 番茄钟 vs 都不做）

### Q4: 书签分类/文件夹如何呈现？
**现状**: Brainstorm 提到"按子文件夹进行分类"，但桌面隐喻下文件夹的呈现方式未定。
**选项**:
- A. 桌面图标直接按文件夹分组（类似 macOS 的文件夹图标，双击打开子桌面）
- B. 单层桌面，分类通过 Dock 栏切换（每个分类是一个 Dock 项，点击切换桌面内容）
- C. 不做分类，所有图标平铺在桌面（最简方案）
**待确认**: MVP 采用哪种分类方案？

---

## 三、交互与体验待决

### Q5: 桌面图标布局是否允许重叠？
**现状**: 用户说"退一万步，把所有书签杂乱堆在屏幕上也是 OK 的"。
**风险**: 如果允许完全自由拖拽（含重叠），图标多了之后难以寻找；如果强制网格对齐，又失去了"桌面"的自由感。
**待确认**: 
- MVP 是否采用网格吸附（类似 iOS 主屏幕）？
- 还是完全自由摆放（类似 macOS 桌面）？

### Q6: 空状态（首次使用无书签）如何引导？
**现状**: 用户首次打开 WebDesk 时，桌面是空的。
**风险**: 空桌面会让用户困惑，不知道下一步该做什么。
**待确认**: 
- 是否预置一组默认书签（如 GitHub、Stack Overflow、Vercel 等开发者常用站）？
- 首次使用时是否弹出引导提示（如"导入书签"或"添加第一个图标"）？

## 四、部署与分发待决

### Q7: 默认部署方案是什么？
**现状**: 提到 GitHub Pages / Vercel / Cloudflare Workers，未确定默认推荐。
**风险**: 不同平台的配置方式不同（GitHub Pages 需启用 Actions，Vercel 需连接仓库），文档和体验差异大。
**待确认**: 
- 默认推荐 GitHub Pages（fork 后直接启用 Actions）？
- 是否同时提供 Vercel 的一键部署按钮？

### Q8: 配置方式：前端界面配置 vs 修改配置文件？
**现状**: Brainstorm 提到"填入自己的 API 或 Token"，但未明确配置入口。
**选项**:
- A. 纯前端配置：用户在 WebDesk 设置面板填写 Token，数据自动同步（最友好）
- B. 配置文件：用户 fork 后修改 `config.json` 再 push（对开发者更熟悉，但流程较重）
- C. 混合：首次使用时前端引导配置，高级设置通过文件修改
**已确认**: ✅ 采用 A（纯前端配置）。设置面板提供 Token + Owner + Repo + Branch 输入，Token 存 localStorage 独立 key，建议使用 Fine-grained Token（仅授权目标仓库 Contents 读写）。

## 五、视觉与品牌待决

### Q9: 壁纸策略是什么？
**现状**: 未提及壁纸来源。
**选项**:
- A. 内置几张精选壁纸供选择
- B. 允许用户上传自定义壁纸
- C. 调用 Unsplash 等 API 动态获取壁纸
- D. 纯色/渐变背景（最简）
**待确认**: MVP 采用哪种壁纸方案？

### Q10: 是否允许用户自定义图标？
**现状**: 未提及用户是否可以上传自己的图标图片替换自动获取的 favicon。
**风险**: 部分网站 favicon 质量差或获取失败，用户可能希望手动替换。
**待确认**: MVP 是否支持用户为单个书签上传自定义图标？还是仅依赖自动获取？

## 六、优先级建议

| 问题 | 建议优先级 | 原因 |
|---|---|---|
| Q1 用户群体 | P1 | 决定产品方向和功能取舍 |
| Q3 本地应用范围 | P1 | 直接影响 MVP 工作量 |
| Q4 分类方案 | P1 | 决定数据结构设计和界面布局 |
| Q6 空状态引导 | P2 | 影响首次使用体验 |
| Q8 配置方式 | P2 | 影响去中心化分发的易用性 |
| Q9 壁纸策略 | P3 | 视觉层，可后续迭代 |
| Q10 自定义图标 | P3 | 锦上添花 |
